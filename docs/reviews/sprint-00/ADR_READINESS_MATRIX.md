# Matriz de preparación de ADRs de SPRINT-00

## Estado del documento

- **Estado:** Propuesta de revisión; no constituye una decisión arquitectónica ni una aprobación.
- **Alcance:** Evaluación de preparación de [ADR-001 a ADR-009](../../decisions/README.md) para la sesión dirigida de SPRINT-00.
- **Estados al elaborar la matriz:** Todos estaban `Proposed`, con fecha `TBD`. Actualización posterior: ADR-001 a ADR-004 y ADR-009 fueron aceptados el 2026-07-21 por la autoridad registrada en cada ADR; sus filas conservan el análisis previo y no prevalecen sobre el [registro](../../decisions/README.md). ADR-003 acepta PostgreSQL 18.x como baseline de R0; ADR-009 acepta repositorio único evolutivo con workspaces bajo demanda, sin seleccionar package manager u orquestador.
- **Autoridad al elaborar la matriz:** `TBD`. Las autoridades aplicadas posteriormente constan en cada ADR aceptado y en el [registro de decisiones](../../decisions/README.md); el gobierno general que no haya sido resuelto continúa abierto.
- **Regla de lectura:** “Puede revisarse ahora” indica que existe material suficiente para una revisión preparatoria de readiness: discutir alternativas, dependencias y el siguiente paso. No significa que el Gate 7 haya comenzado formalmente ni equivale a validación o aceptación. La revisión formal de cada ADR espera los gates de producto que figuran en su fila.

## Criterios de evaluación

La matriz distingue entre:

- dependencia de producto, que sólo puede cerrarse con decisiones trazables sobre alcance, operación o mercado;
- dependencia técnica, que requiere análisis de arquitectura, seguridad u operaciones;
- evidencia documental existente frente a evidencia experimental todavía ausente;
- benchmark, que compara comportamiento medible bajo un escenario definido;
- spike, que reduce una incertidumbre técnica acotada y puede concluir aceptando o rechazando la hipótesis;
- recomendación de revisión, que no modifica el estado del ADR.

Las recomendaciones usan exclusivamente: `Keep Proposed`, `Ready for Product Owner review`, `Ready for technical validation`, `Split ADR`, `Merge with another ADR` o `Reject proposal`.

## Decisiones derivadas que no deben ocultarse

- **ORM o query builder:** Prisma, Drizzle u otra alternativa requieren un ADR futuro separado. La decisión debe considerar transacciones, migraciones, constraints compuestos, pooling y compatibilidad con RLS; no pertenece implícitamente a ADR-003 ni ADR-005.
- **Proveedor de PostgreSQL:** ADR-003 acepta PostgreSQL y la baseline 18.x, pero no selecciona región, servicio administrado, extensión, pooler ni versión minor inmutable.
- **RLS:** es opcional y pendiente de spike. Si se adopta, su alcance, roles, políticas y operación deben quedar en una decisión derivada de ADR-003/004 con evidencia de SPIKE-003.
- **Web:** Tailwind CSS y el design system siguen siendo hipótesis independientes de ADR-006 y dependen de [QUESTION-031](../../product/OPEN_QUESTIONS.md#question-031) y [QUESTION-032](../../product/OPEN_QUESTIONS.md#question-032).
- **Entrega:** GitHub Actions, Docker Compose, registry y plataforma de ejecución no quedan aprobados por revisar ADR-007; Node.js `24.x` fue aceptado separadamente por ADR-001.
- **Repositorio único:** ADR-009 quedó aceptado, pero pnpm, Turborepo, Nx, versionado independiente, publicación de packages y caché remota no quedaron aprobados.
- **Realtime, colas y objetos:** Redis/BullMQ, Socket.IO/WebSockets y almacenamiento S3-compatible siguen siendo candidatos. Requerirán decisiones cuando producto confirme los recorridos que los necesitan.

## Orden técnico recomendado dentro del Gate 7

Este orden sólo aplica después de completar los gates de producto y operación correspondientes:

1. ADR-001 y ADR-002 ya fueron aceptados; aplicar sus límites como entradas de las revisiones restantes.
2. ADR-003 ya fue aceptado al nivel de motor, sin mezclar proveedor, ORM o RLS.
3. Con organización, identidad y datos definidos, validar la aplicación de ADR-004 mediante SPIKE-002; ejecutar SPIKE-003 sólo antes de adoptar RLS.
4. Con identidad, sesión y dominios definidos, validar ADR-008 mediante SPIKE-001.
5. Ejecutar y revisar SPIKE-009, ya autorizado como `Mandatory before acceptance`, antes de decidir ADR-005; dividir o acotar ADR-006 después de confirmar superficies.
6. Aplicar ADR-009 como repositorio único sin workspaces obligatorios; evaluar tooling sólo cuando exista un grafo real autorizado.
7. Validar ADR-007 al nivel de empaquetado y promoción, manteniendo tooling y proveedor como decisiones separadas.
