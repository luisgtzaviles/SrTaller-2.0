## Objetivo

Persistir roles tenant-scoped, sus capabilities y assignments aplicables al
Tenant completo o a una Branch, sin convertir el nombre del rol, la UI o el
cliente en autoridad.

## Contrato aprobado

- Múltiples roles por User.
- Scope `TENANT_WIDE` o `BRANCH_RESTRICTED`.
- Unión determinista de capabilities aplicables a la Branch efectiva.
- Sin permisos directos por User, deny rules particulares, herencia compleja
  ni ABAC general.
- Starter roles configurados por Tenant: `Administrador`, `Atención al
  cliente` y `Técnico`; sus nombres no otorgan autoridad.
- Catálogo mínimo de este checkpoint:
  - `users.read`;
  - `access_matrix.read`;
  - `repairs.read`;
  - `repairs.add_note`.
- `sessions.start` no es una capability: la elegibilidad pre-autenticación y la
  autorización de una operación protegida son responsabilidades distintas.

## Alcance

- Catálogo cerrado de las cuatro capabilities necesarias para el checkpoint.
- Roles tenant-scoped, composición rol–capability y estados de rol.
- Assign/revoke server-only con historial durable, idempotencia,
  `expectedVersion` para revocación y protección de concurrencia.
- Assignments tenant-wide o restringidos a una Branch del mismo Tenant.
- Read models para matriz de acceso, Users con assignments aplicables a una
  Branch y unión de grants por capabilities.
- Migraciones aditivas, constraints y fixtures locales/test.
- Registro de ownership `access` conforme a DEC-005/DEC-049.

## Fuera de alcance

- Endpoints o editor productivo de roles/assignments.
- Permisos directos por User, roles heredados, denies explícitos o ABAC.
- PIN, Operational Session, login, cookies o credenciales.
- Enforcement final de operaciones protegidas; pertenece a PBI-026.
- Autorización reforzada, reautenticación o segundo aprobador; pertenece a
  PBI-035.
- Auditoría extendida, administración de Station, deploy o release.

## Criterios de aceptación

- Los roles y assignments de otro Tenant no son observables ni utilizables.
- Un User, Role y Branch deben pertenecer al mismo Tenant para crear una
  asignación.
- Una asignación restringida sólo aporta capabilities en su Branch; una
  tenant-wide mantiene movilidad entre Branches del mismo Tenant.
- Múltiples roles activos componen una unión estable sin autoridad por nombre.
- Roles `disabled`/`archived` y assignments revocados no aportan grants. Un
  User no activo puede conservar assignments como historia/configuración,
  pero PBI-026 debe intersectar el grant con el estado activo del User y el
  contexto confiable antes de autorizar cualquier operación.
- Assign/revoke son atómicos, idempotentes y fail-closed ante replay divergente
  o `expectedVersion` obsoleta.
- PostgreSQL real prueba constraints, rollback/reapply, aislamiento,
  concurrencia e idempotencia.
- No se expone una superficie HTTP/UI que eluda PBI-026.
- Arquitectura, typecheck, build, `pnpm run verify`, secret scan y CI
  autoritativo pasan sobre el candidate exacto antes del focused review.
