## Objetivo

Materializar el contrato técnico ya aceptado por DEC-004 y producir evidencia verificable para VC-001 a VC-024, sin incorporar funcionalidad de producto ni declarar reproducibilidad antes de completar y revisar la evidencia autoritativa Linux.

## Contexto

DEC-004 está `Accepted — Selection Approved / Evidence Pending`. La selección de Node.js, pnpm, lockfile, módulos, TypeScript, build, ejecución, supply chain y plataforma autoritativa es normativa y no se reabre en este PBI.

La [revisión formal](../../decisions/dec-004-toolchain-contract/FORMAL_REVIEW.md) autorizó este trabajo. El [contrato de verificación](../../decisions/dec-004-toolchain-contract/VERIFICATION_CONTRACT.md) define VC-001 a VC-024, pero ninguno ha sido ejecutado. La aceptación de la selección no equivale a materialización; materializar no equivale automáticamente a verificar; y un build aislado, especialmente en macOS, no demuestra reproducibilidad.

## Valor esperado

- Convertir una selección documental en un baseline mínimo ejecutable y auditable.
- Hacer que versiones, lockfile y rutas de ejecución incompatibles fallen temprano.
- Producir evidencia comparable sobre Linux x86_64/glibc.
- Separar el cumplimiento del toolchain de cualquier funcionalidad de SR Taller 2.0.
- Permitir una revisión objetiva de DEC-004 sin depender de SPIKE-009, tooling global, IDE o afirmaciones manuales.

## Alcance incluido

La tarea de ejecución queda autorizada para crear únicamente lo mínimo necesario para satisfacer el contrato:

- pins exactos de Node.js `24.18.0` mediante `.nvmrc`, `.node-version`, `engines.node` y comprobación fail-fast;
- pin exacto de pnpm `11.15.1` mediante `packageManager`, mecanismos compatibles y comprobación fail-fast;
- un único `pnpm-lock.yaml` generado y revisado en la tarea de materialización;
- configuración raíz de pnpm para instalación frozen, bloqueo de scripts de dependencias y allowlist gobernada;
- manifiesto raíz para una sola aplicación y un solo artefacto iniciales;
- TypeScript `6.0.3` exacta, local y en modo estricto;
- configuración ESM nativa con `type: module`, `module: NodeNext` y `moduleResolution: NodeNext`;
- `tsconfig.json` y `tsconfig.build.json` con fuente bajo `src/` y salida exclusiva bajo `dist/`;
- shell técnico mínimo compilable compatible con NestJS `11.x`, referencia `11.1.28`, Express y REST/HTTP JSON mínima;
- bootstrap, provider o controller técnico mínimo sólo cuando sea necesario para VC-013, sin capacidad de negocio;
- scripts independientes del IDE para `verify:toolchain`, `clean`, `typecheck`, `build`, `test`, `start`, `dev` y `verify`;
- desarrollo mediante `tsc --watch` y ejecución del JavaScript emitido;
- producción de prueba mediante JavaScript compilado desde `dist/`, nunca TypeScript directo;
- comprobaciones automatizadas específicas de DEC-004 usando únicamente la baseline aprobada y sin elegir un runner general reservado a DEC-051;
- materialización y prueba del bloqueo de scripts de dependencias y de una allowlist explícita, mínima, justificada, revisable y versionada;
- ejecución local diagnóstica en macOS cuando aporte feedback, sin tratarla como evidencia final;
- ejecución autoritativa en Linux x86_64/glibc;
- dos directorios Linux independientes, inventarios normalizados y SHA-256 comparables de `dist/`;
- evidencia sanitizada, resultados por VC y registro de riesgos residuales.

## Decisiones de alcance específicas

### Repositorio y workspace

R0 conserva una sola aplicación y un solo artefacto. pnpm no autoriza por sí mismo workspaces. Por tanto:

- el baseline se materializará como paquete/aplicación raíz mínima;
- no se creará `pnpm-workspace.yaml` ni un workspace vacío o anticipatorio;
- un workspace sólo podrá introducirse si aparece más de un proyecto real y la autoridad de ADR-009/DEC-005 lo aprueba por separado.

### Shell técnico y rutas HTTP

El shell mínimo no incluye lógica funcional. El contrato permite comprobar startup, listener y lifecycle, pero no autoriza un endpoint por preferencia:

- no se crea `/health` en este PBI salvo autorización documental posterior explícita;
- un controller/provider vacío o técnico sólo puede existir para demostrar VC-013;
- ninguna ruta puede exponer datos, comportamiento de negocio o contrato público definitivo.

### Script `test`

El nombre `test` es obligatorio como contrato estable, pero DEC-051 conserva la selección del runner, suites y cobertura generales. La materialización podrá usar comprobaciones técnicas acotadas construidas con la baseline aprobada; no podrá adoptar Jest, Vitest, Supertest u otro runner general sin decisión aplicable.

## Alcance excluido

- lógica funcional de Reparaciones o de cualquier otro módulo;
- modelado nuevo de dominio, agregados, comandos, eventos o reglas de negocio;
- APIs funcionales, contratos públicos o `/health` no autorizado;
- persistencia funcional, conexión a PostgreSQL, repositories, transacciones o pool;
- SQL, esquemas, datos, seeds o migraciones;
- autenticación, PIN, sesiones, multitenancy, autorización o auditoría funcional;
- UI, clientes web, realtime, jobs, caché o integraciones;
- Dockerfile, contenedores, registry, proveedor de CI, hosting o despliegue productivo;
- selección de runner, cobertura o gate general perteneciente a DEC-051;
- estructura modular definitiva, ownership o enforcement perteneciente a DEC-005;
- errores de producto pertenecientes a DEC-044;
- reutilización o copia de SPIKE-009 como scaffold;
- cambio, reinterpretación o sustitución de DEC-004;
- cierre anticipado o declaración falsa de reproducibilidad.

## Política de fallos

- Cualquier fallo se conserva con comando, plataforma, exit code y log sanitizado.
- No se cambian versiones, ESM, compilador, gestor o estrategia para “poner verde” el gate sin autoridad.
- No se regenera silenciosamente el lockfile ni se corrige automáticamente el repositorio durante un caso negativo.
- Un caso negativo que no falle como se esperaba es `FAIL`, no una observación menor.
- Un resultado sólo macOS, VC faltante o revisión obligatoria ausente no puede producir `PASS`.
- Si VC-024 espera DEC-051, el máximo resultado es `CONDITIONAL PASS`; DEC-004 conserva `Evidence Pending`.
- Una incompatibilidad material se escala para remediar dentro del contrato o reabrir DEC-004; no se introduce CommonJS, otro runtime o tooling alterno silenciosamente.
- Fixtures y copias temporales se eliminan después de conservar evidencia; no se revierten cambios ajenos del working tree original.

## Definición de terminado del PBI

PBI-021 sólo puede pasar a `Done` cuando:

- todos sus criterios de aceptación aplicables están satisfechos;
- VC-001 a VC-024 tienen resultado y evidencia revisada sobre la plataforma requerida;
- no queda ningún `Pending`, `Not run` o equivalente en la matriz obligatoria;
- el resultado final es `PASS`, no sólo éxito local o build aislado;
- el árbol candidato queda sin mutaciones inesperadas;
- los riesgos residuales están mitigados o aceptados por su autoridad;
- las revisiones de Seguridad, Operaciones y Calidad están registradas;
- Arquitectura + Ingeniería aprueban el resultado del PBI;
- no se incorporó funcionalidad ni se invadieron DEC-005/044/049/050/051/063;
- la evidencia está vinculada al mismo commit y no contiene secretos;
- el cambio de estado posterior de DEC-004, si corresponde, se realiza en una decisión/revisión separada.

## Condiciones que no autorizan cerrar DEC-004

No basta con:

- crear archivos de configuración;
- instalar dependencias una vez;
- compilar o iniciar una vez;
- pasar en macOS;
- ejecutar sólo casos positivos;
- obtener hashes de un solo directorio;
- repetir en el mismo `node_modules` o compartir salida construida;
- completar VC-001 a VC-023 sin VC-024;
- marcar PBI-021 `Done` sin revisión de evidencia;
- recibir una aprobación verbal no registrada.

Incluso con PBI-021 `Done`, DEC-004 permanece `Evidence Pending` hasta que la autoridad ejecute una revisión separada y registre el estado resultante.
