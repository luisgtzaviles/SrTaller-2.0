# PBI-023 — Establish tenant-scoped persistence and migration foundation

## Estado

- **Estado:** `Ready — tenant schema verified / owner-scoped adapters
  authorized`.
- **Ejecución:** Paso 9 completo; existen facility, transaction runner,
  migration runner y schema mínimo `tenants`/`branches` verificados, sin
  conexión en startup, adapters, repositories ni persistencia funcional.
- **Epic:** EPIC-001 — Engineering Foundation.
- **Tipo:** Technical foundation / Persistence / Security / Quality.
- **Riesgo:** alto, fail-closed.
- **Owner de ejecución:** Ingeniería.
- **Owners de control:** Arquitectura, Seguridad, Operaciones y Calidad.
- **Hito comprometido:** SPIKE-002, checker/boundaries, dependencias exactas,
  configuración tipada, facility de conexión, transaction runner y migration
  runner y primera migración cerrados; el siguiente gate son ports/adapters
  owner-scoped. La
  implementación no está comprometida a sprint.
- **Estimación:** `13 Story Points` (Fibonacci), riesgo alto e incertidumbre
  media-alta; requiere reestimación si cambian los supuestos del
  [expediente](../../architecture-readiness/pbi-023/ESTIMATION.md).

## Objetivo y valor

Crear la primera fundación persistente de R0: PostgreSQL 18.4 reproducible,
migraciones gobernadas y repositorios tenant-scoped que demuestren con dos
tenants sintéticos que el acceso cruzado falla, sin exponer API ni implementar
identidad, sesiones o negocio.

## Alcance

- Resolver y registrar DEC-050 antes de instalar migrador o crear migración.
- Ejecutar SPIKE-002 acotado antes de persistencia tenant-scoped.
- Materializar DEC051-C03/C04/C06 y DEC063-C02/C05/C06 antes de sus triggers.
- Aplicar DEC049-C01–C08 al alcance mínimo.
- Crear únicamente objetos base de tenant y la infraestructura necesaria para
  demostrar ownership, scope y constraints.
- Probar dos tenants, referencias cruzadas, omisión/conflicto de scope,
  commit/rollback y cleanup.
- Materializar fixtures sintéticos deterministas de DEC-052.
- Usar credenciales de test efímeras; no crear secretos de ambiente compartido.

- Reparaciones, clientes, inventario o cualquier regla de negocio.

La [revisión final](../../architecture-readiness/R0_AUTHORIZATION.md) confirmó
`Ready` con notas no bloqueantes y autorizó exclusivamente este PBI. La
autorización no equivale a `In progress`: antes de comprometerlo a un sprint
debe acordarse la estimación y su ejecución debe respetar el orden fail-closed
de DEC-050, SPIKE-002 y las condiciones aplicables.

La planificación del 2026-07-24 aceptó
[DEC-050](../../decisions/dec-050-migration-strategy/DECISION_PROPOSAL.md) con
condiciones y fijó la estimación. La ejecución separada del 2026-07-25 cerró
[SPIKE-002](../../architecture-readiness/pbi-023/spike-002-evidence/RESULTS.md)
con PostgreSQL real, E1–E12, dos runs, comparación y cleanup `PASS`. El Paso 3
agregó D5-R037–D5-R047 sin tocar `src/`. El estado vigente tras el Paso 9 y
D5-R053 es 160 fixtures y 40 mutaciones de producto. El PBI
queda `Ready`, no `In progress`, `Implemented` ni `Done`. El Paso 4 instaló
`kysely@0.29.4`, `pg@8.22.0` y `@types/pg@8.20.0`, pasó tres ciclos de gates y
dos reinstalaciones limpias; no creó código ni conexión. Su
[evidencia](../../architecture-readiness/pbi-023/dependency-installation/README.md)
mantiene runtime, migraciones y PostgreSQL CI pendientes.

El Paso 5 materializó la configuración tipada. El Paso 6 materializó
`database-connection.ts` con `pg.Pool`, `Kysely` + `PostgresDialect`, apertura
lazy, probe único `select 1`, estados explícitos, errores estables, redacción y
cierre idempotente. Dos runs locales limpios contra PostgreSQL `18.4`
confirmaron autenticación negativa, base inexistente, timeout, SSL incompatible,
pool/release, concurrencia, cierre y ausencia de objetos. Esta evidencia no
satisface DEC051-C03 en CI ni autoriza migraciones o tablas.

El Paso 7 materializó `transaction-runner.ts` y una capability Kysely
owner-internal sin ampliar `DatabaseConnection`. Pruebas unitarias y dos runs
PostgreSQL `18.4` verificaron commit, rollback, niveles de aislamiento,
read-only, `40001`, `40P01`, `57014`, nesting, cierre, concurrencia,
sanitización y cleanup. D5-R048 protege la frontera. No se crearon migraciones,
tablas productivas, repositories, adapters ni wiring.

El Paso 8 materializó `migration-runner.ts`, capability y provider
owner-internal, `Kysely.Migrator`, `FileMigrationProvider`, manifest SHA-256,
status, up/down gobernado, journal y advisory lock con timeout. Dos runs
PostgreSQL `18.4` comprobaron orden, re-run, rollback, drift, concurrencia,
cleanup y ejecución ESM/NodeNext desde `dist`. D5-R049 impide consumo desde
startup/capas funcionales.

El Paso 9 creó una sola migración central y únicamente `tenants`/`branches`.
Dos runs PostgreSQL `18.4` verificaron introspección exacta, constraints,
índices, aislamiento estructural negativo, FK futura compuesta, up/down,
reapply, atomicidad, manifest/drift y cleanup. D5-R050–D5-R053 protegen el
contrato. No se crearon repositories, adapters, ports, seeds ni wiring.
