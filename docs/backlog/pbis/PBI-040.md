## Problema

Un empleado no tiene una referencia rápida y gobernada para responder cuánto
cuesta una refacción, producto o servicio en su sucursal. Crear sólo una tabla o
una pantalla obligaría después a Inventory, Repair o Caja a depender de datos
sin identidad, procedencia o historia segura.

## Valor esperado

Un usuario autorizado registra individualmente un artículo comercial y su
precio; cualquier empleado con acceso lo encuentra en segundos por nombre, SKU
o código y ve el precio efectivo de su Branch con moneda y procedencia. El
resultado persiste, respeta Tenant/Branch y queda listo para ser consumido por
contratos futuros sin entregar ownership.

## Alcance

- Materializar el módulo `catalog` sólo cuando contenga el slice funcional y
  registrarlo en DEC-005/policy/grafo/ownership en el mismo cambio.
- `CatalogItem` Tenant-scoped, tipos Refacción/Producto/Servicio/Insumo,
  lifecycle, capabilities gobernadas, categoría plana y marca comercial.
- SKU y código de barras internos Tenant-wide, aportados o generados
  server-side. Code 128 queda reservado como representación futura del barcode,
  no como un tercer identificador.
- `Tenant.operatingCurrency` con Avicell `MXN` como dato configurado, no
  hardcode; sin UI de cambio de moneda.
- Revisión de precio base, override opcional Branch, revocación que restaura
  herencia y costo de referencia opcional con procedencia.
- Alta/edición individual Owner-friendly, sin imagen en este PBI.
- `Listas > Lista de precios` como única entrada inicial del grupo; búsqueda,
  filtros, estados y procedencia de precio.
- Gobierno centralizado en `Configuración > Catálogos > Lista de precios`,
  aplicabilidad por Tipo, Category/Brand escribibles y reconciliables y valores
  inline Por revisar.
- Filtro administrativo `Todos | Refacción | Servicio | Producto | Insumo`
  derivado de esa misma aplicabilidad para canónicas y pendientes.
- Lifecycle administrativo compartido: hard delete únicamente para referencias
  canónicas sin uso/dependencias reales, deactivación para usadas, reactivación
  para inactivas y reconciliación separada para capturas pendientes.
- SKU y código de barras automáticos server-side cuando quedan vacíos; los
  valores explícitos se normalizan, preservan y son únicos Tenant-wide.
- Capabilities, preferencia personal de costo default oculta, auditoría,
  idempotencia, optimistic concurrency y contratos públicos mínimos.
- Evidencia automatizada, UI formal, aislamiento, migración/rollback y runtime
  proporcional al riesgo.

## Fuera de alcance

## Actores y escenarios

- **Empleado con `price_list.read`:** consulta desde una estación/sesión con
  Branch confiable.
- **Administrador de catálogo:** crea/edita identidad, clasificación y precios
  según sus capabilities; administración tenant-wide usa contexto explícito.
- **Usuario autorizado a costo:** puede activar su preferencia personal; el
  backend no entrega costo sin `catalog.reference_cost.read`.
- **Casos:** pantalla OLED vs LCD; servicio 350/399; termo no telefónico; insumo
  alcohol excluido; dos Branches con herencia distinta.

## Criterios de aceptación

### Resultado visible

- [x] Un administrador crea una Refacción, Producto o Servicio con título,
  descripción opcional, categoría, marca opcional, costo opcional, precio,
  SKU y código de barras aportados o automáticos; reload conserva ambos datos.
- [x] Título, descripción y nombre normalizados no determinan identidad ni
  fusionan OLED/LCD.
- [x] Un usuario con `price_list.read` busca por tokens de nombre o exacto por
  SKU/barcode y obtiene sólo items activos vendibles del Tenant.
- [x] Cada resultado muestra tipo, categoría, marca cuando aplica, precio
  efectivo, moneda Tenant y `Base Tenant` o `Override Branch`.
- [x] Un Servicio puede carecer de costo y stock; un Producto como termo no
  depende de Repairs; un Insumo existe en catálogo pero no aparece en la lista.
- [x] Crear override 399 sobre base 350 afecta sólo la Branch objetivo; revocarlo
  vuelve a 350 sin copiar la base ni alterar otras Branches.

### Seguridad, datos y errores

- [x] Tenant/Branch se derivan server-side; IDs ajenos/inexistentes producen
  respuesta no reveladora y no se filtran en errores de unicidad.
- [x] Sin `catalog.reference_cost.read`, ningún contrato de búsqueda devuelve
  el costo. Con capability, el costo sólo se solicita/muestra cuando la
  preferencia personal `priceListShowReferenceCost` está activa; default false.
- [x] Cada write exige capability, CSRF/idempotencia aplicable,
  `expectedVersion`, actor y audit/correlation; stale devuelve conflicto sin
  sobrescritura.
- [x] SKU y código de barras son únicos Tenant-wide por scheme bajo concurrencia y no
  se reutilizan tras inactivar.
- [x] Base, override y costo conservan revisiones append-only con procedencia;
  no se presentan como costo contable o inventario.
- [x] Migración de expansión, backfill MXN explícito para Avicell, rollback de
  aplicación y compatibilidad quedan probados conforme a DEC-050.

### UX y rendimiento

- [x] Sidebar muestra grupo `Listas` con sólo `Lista de precios`; no muestra
  Pedidos/Solicitudes placeholders ni Lista de precios bajo Operación.
- [x] Lista/alta/edición cubren loading, empty, error, permission denied,
  not-priced, inactive, long content, keyboard, focus, responsive y Light/Dark.
- [x] La búsqueda usa paginación/orden estable e índices Tenant-aware; una
  prueba con 10,000 items sintéticos registra p95 local y el presupuesto se fija
  antes de Owner QA sin cargar todo al browser.
- [x] Category y Brand usan autocomplete compartido, teclado/mouse/ARIA y crean
  sólo por intención explícita; el draft se conserva y blur no persiste.
- [x] Category tiene un Tipo aplicable y Brand uno o varios; el servidor rechaza
  combinaciones incompatibles y cambiar Tipo limpia e informa las selecciones
  que dejan de aplicar.
- [x] Los valores inline quedan como referencias capturadas Por revisar y nunca

## Cierre

La iteración Owner vigente conserva SKU y código de barras como únicos
identificadores internos y converge los módulos de Catálogos sobre una misma
estructura visual. La auditoría posterior confirmó que PBI-039 permanece en el
ancestry y en 16 superficies protegidas. Los catálogos sintéticos locales no
crean vínculos para Repairs históricas por coincidencia textual; el contador
visible declara ahora su semántica canónica.
El checkpoint permanece sobre `feature/pbi-040-catalog-pricing-core`. Quedan
pendientes Owner Review/Owner Acceptance, revisión independiente y los gates
posteriores de PR/CI/merge.
No existen push, PR, merge, deploy, release ni Owner Acceptance para PBI-040.
La reconciliación posterior probó que Preview materializa `0d1c576…`, que es
ancestro directo de la baseline integrada `40684d7…`, y que Repair Detail es
igual runtime contra runtime al usar el mismo read model materializado
`SR-2026-039`. El launcher local queda protegido contra
frontend/backend/build stale y el nuevo guard protege read model, DOM y assets
Preview sin cambiar producto.
La iteración de referencias exactas aplica identidad Category Tenant+Tipo y
Brand Tenant-wide antes de crear pending, conserva near matches y amplía
aplicabilidad de Brand con audit. El candidato `f4ace4a` pasó `verify:full`
13/13 y el duplicado sintético histórico fue asociado al canon por la
reconciliación gobernada, sin borrar su captura ni su procedencia.
La iteración actual separa explícitamente Edit, Pending Reconciliation y
Canonical Merge. Category/Brand canónicas pueden consolidarse en una
superviviente con reasignación, unión de aplicabilidad y evento append-only; las
fuentes se preservan como merged. La edición de item usa ahora el mismo contrato
inline que la creación. Repairs conserva ownership y su posible merge queda
diferido por las decisiones documentadas en la auditoría de aplicabilidad.
