## Problema

Un empleado no tiene una referencia rápida y gobernada para responder cuánto
cuesta una refacción, producto o servicio en su sucursal. Crear sólo una tabla o
una pantalla obligaría después a Inventory, Repair o Caja a depender de datos
sin identidad, procedencia o historia segura.

## Valor esperado

Un usuario autorizado registra individualmente un artículo comercial y su
precio; cualquier empleado con acceso lo encuentra en segundos por nombre, SKU
o código y ve el precio efectivo de su Branch con moneda y procedencia. El
resultado persiste, respeta Tenant/Branch y queda listo para ser consumido por
contratos futuros sin entregar ownership.

## Alcance

- Materializar el módulo `catalog` sólo cuando contenga el slice funcional y
  registrarlo en DEC-005/policy/grafo/ownership en el mismo cambio.
- `CatalogItem` Tenant-scoped, tipos Refacción/Producto/Servicio/Insumo,
  lifecycle, capabilities gobernadas, categoría plana y marca comercial.
- SKU Tenant-wide aportado o generado server-side; barcode interno opcional y
  GTIN tipado/validado.
- `Tenant.operatingCurrency` con Avicell `MXN` como dato configurado, no
  hardcode; sin UI de cambio de moneda.
- Revisión de precio base, override opcional Branch, revocación que restaura
  herencia y costo de referencia opcional con procedencia.
- Alta/edición individual Owner-friendly, sin imagen en este PBI.
- `Listas > Lista de precios` como única entrada inicial del grupo; búsqueda,
  filtros, estados y procedencia de precio.
- Capabilities, preferencia personal de costo default oculta, auditoría,
  idempotencia, optimistic concurrency y contratos públicos mínimos.
- Evidencia automatizada, UI formal, aislamiento, migración/rollback y runtime
  proporcional al riesgo.

## Fuera de alcance

- Importación masiva, proveedor maestro y compras.
- Imagen/Files; perfiles compartidos; multi-currency/FX; impuestos, descuentos,
  cotización o autorización comercial.
- Existencia, reservas, movimientos, valuación y cualquier pantalla Inventory.
- Repair Concepts, ventas, Payments, Caja, pedidos, solicitudes o reportes.
- Árbol de categorías, catálogo Platform, fuzzy matching, sync con
  `repair_brands`, eventos distribuidos o microservicios.

## Actores y escenarios

- **Empleado con `price_list.read`:** consulta desde una estación/sesión con
  Branch confiable.
- **Administrador de catálogo:** crea/edita identidad, clasificación y precios
  según sus capabilities; administración tenant-wide usa contexto explícito.
- **Usuario autorizado a costo:** puede activar su preferencia personal; el
  backend no entrega costo sin `catalog.reference_cost.read`.
- **Casos:** pantalla OLED vs LCD; servicio 350/399; termo no telefónico; insumo
  alcohol excluido; dos Branches con herencia distinta.

## Criterios de aceptación

### Resultado visible

- [ ] Un administrador crea una Refacción, Producto o Servicio con título,
  descripción opcional, categoría, marca opcional, costo opcional, precio,
  SKU aportado o automático y barcode/GTIN opcional; reload conserva el dato.
- [ ] Título, descripción y nombre normalizados no determinan identidad ni
  fusionan OLED/LCD.
- [ ] Un usuario con `price_list.read` busca por tokens de nombre o exacto por
  SKU/barcode y obtiene sólo items activos vendibles del Tenant.
- [ ] Cada resultado muestra tipo, categoría, marca cuando aplica, precio
  efectivo, moneda Tenant y `Base Tenant` o `Override Branch`.
- [ ] Un Servicio puede carecer de costo y stock; un Producto como termo no
  depende de Repairs; un Insumo existe en catálogo pero no aparece en la lista.
- [ ] Crear override 399 sobre base 350 afecta sólo la Branch objetivo; revocarlo
  vuelve a 350 sin copiar la base ni alterar otras Branches.

### Seguridad, datos y errores

- [ ] Tenant/Branch se derivan server-side; IDs ajenos/inexistentes producen
  respuesta no reveladora y no se filtran en errores de unicidad.
- [ ] Sin `catalog.reference_cost.read`, ningún contrato de búsqueda devuelve
  el costo. Con capability, el costo sólo se solicita/muestra cuando la
  preferencia personal `priceListShowReferenceCost` está activa; default false.
- [ ] Cada write exige capability, CSRF/idempotencia aplicable,
  `expectedVersion`, actor y audit/correlation; stale devuelve conflicto sin
  sobrescritura.
- [ ] SKU/barcode/GTIN son únicos Tenant-wide por scheme bajo concurrencia y no
  se reutilizan tras inactivar.
- [ ] Base, override y costo conservan revisiones append-only con procedencia;
  no se presentan como costo contable o inventario.
- [ ] Migración de expansión, backfill MXN explícito para Avicell, rollback de
  aplicación y compatibilidad quedan probados conforme a DEC-050.

### UX y rendimiento

- [ ] Sidebar muestra grupo `Listas` con sólo `Lista de precios`; no muestra
  Pedidos/Solicitudes placeholders ni Lista de precios bajo Operación.
- [ ] Lista/alta/edición cubren loading, empty, error, permission denied,
  not-priced, inactive, long content, keyboard, focus, responsive y Light/Dark.
- [ ] La búsqueda usa paginación/orden estable e índices Tenant-aware; una
  prueba con 10,000 items sintéticos registra p95 local y el presupuesto se fija
  antes de Owner QA sin cargar todo al browser.
- [ ] Chrome real prueba alta, búsqueda por las tres vías, override/herencia,
  costo autorizado/no autorizado y reload en al menos dos Branches/dos Tenants.

## Estrategia de implementación y pruebas

Checkpoints dentro del mismo WIP:

1. **A — Domain/data/security:** modelo, invariantes, migraciones, repositories,
   public contracts, capabilities y pruebas unitarias/PG/aislamiento/concurrencia.
2. **B — Individual management:** API/UI de alta/edición, lifecycle, precios,
   overrides, costo y preferencia personal.
3. **C — Fast lookup:** navegación, búsqueda indexada, estados y branch price.
4. **D — Verification/delivery:** architecture checks, full verify, formal UI,
   focused high-risk review, CI, Owner QA y gates de merge/deploy separados.

Pruebas mínimas: unidad de resolución/normalización, integración PostgreSQL,
contract/API, capabilities negativas, dos Tenants/dos Branches, carrera de
identificador/version, migration up/compatibility, frontend contracts,
accessibility/responsive, benchmark 10k y navegador real.

## Rollout y rollback

- Entregar por migraciones de expansión antes del código que lee los datos.
- Feature no se anuncia disponible hasta que currency/capabilities/defaults e
  índices estén presentes y exact-main CI/Preview validation pasen.
- Rollback de aplicación mantiene tablas/revisiones; no borra precios. Una
  migración destructiva queda fuera.
- Production requiere autorización independiente; Preview no implica release.
