# PBI-026 — Contextual Authorization

## Estado

- **Estado:** In progress; local integration candidate, not integrated.
- **Tipo:** Authorization / Security Foundation.
- **Owner:** Producto + Seguridad + Arquitectura + Ingeniería.
- **Riesgo:** Critical — clasificación preservada; es el trust boundary de
  autorización ya previsto por el `Identity Master Goal`, no un Critical nuevo.
- **Estimación:** Large.
- **Sprint:** SPRINT-02 — PBI actual; WIP `1/1`.

## Objetivo observable

Permitir una operación de Repairs únicamente cuando una Station confiable, una
Operational Session vigente, un User activo, sus assignments aplicables y una
capability fresca autorizan exactamente esa acción y el recurso pertenece al
Tenant/Branch efectivo. Cualquier predicado ausente, inválido, revocado,
manipulado o fuera de scope falla cerrado antes de efectos.

## Contrato autorizado

- Tenant, Branch, Station, Session y User se resuelven server-side; nunca desde
  IDs, roles, capabilities o contexto enviados por el cliente.
- El nombre del role no concede autoridad. Se usa la unión fresca de
  capabilities de assignments activos aplicables al Branch actual.
- La autorización se reevalúa en cada operación protegida, sin cache
  autoritativa ni verdict reutilizable por el navegador.
- El recurso de negocio continúa siendo Repairs-owned y se resuelve dentro del
  Tenant/Branch autorizado.
- La UI proyecta capabilities sólo para affordances; el servidor conserva el
  enforcement completo.
- Una revocación ya comprometida antes de la siguiente decisión de
  autorización se observa en esa operación. Un efecto ya autorizado puede
  linearizar antes de una revocación concurrente posterior.

## Matriz inicial de acciones

| Superficie | Capability / política | Scope |
|---|---|---|
| `GET /api/repairs` | `repairs.read` | Worklist del Branch efectivo |
| `GET /api/repairs/technicians` | `repairs.read` | Proyección read-only del Branch efectivo |
| `GET /api/repairs/:id` | `repairs.read` | Repair del Tenant/Branch efectivo |
| `GET /api/repairs/:repairId/evidence/:evidenceId/content` | `repairs.read` | Evidence subordinada al Repair autorizado |
| `POST /api/repairs/:repairId/notes` | `repairs.add_note` + same-origin JSON + CSRF | Repair del Tenant/Branch efectivo |
| assignment/reassignment/unassignment, start diagnosis, move workshop | `DENY_UNSUPPORTED` | Sin capability aprobada en el catálogo mínimo |

Las mutaciones D5/D6 permanecen implementadas y testeadas como dominio
histórico, pero no son invocables desde HTTP/UI hasta que un PBI autorizado
introduzca capabilities específicas. No se reutiliza `repairs.add_note` ni se
inventan permisos.

## Composición DEC-005

Se materializa una única arista dirigida adicional:

```text
repairs -> access -> stations
                  -> users
```

Access publica un token y contrato framework-neutral de autorización
contextual. Repairs importa únicamente esa superficie pública, fija la
capability por operación y conserva ownership del recurso. Quedan prohibidos
la arista inversa, deep/private imports, repository bypass, `ModuleRef`,
`forwardRef`, módulos globales y service locators.

## Errores y transporte

- Station/Session/User inválidos o ausentes: `401 AUTHENTICATION_REQUIRED`.
- Actor autenticado sin capability, o mutación sin CSRF/origen/JSON válido:
  `403 ACCESS_DENIED`.
- Repair inexistente o foreign Tenant/Branch: la misma respuesta scoped
  `404 REPAIR_NOT_FOUND`, sólo después de autorización. Evidence inexistente,
  foreign o sin contenido material conserva `404 REPAIR_EVIDENCE_NOT_FOUND`;
  ninguna variante revela si el recurso existe fuera del scope efectivo.
- Dependencia de autoridad no disponible: fail-closed, respuesta sanitizada y
  cero efectos.
- Respuestas protegidas: `Cache-Control: private, no-store`.

## Fuera de alcance

- Capabilities nuevas para D5/D6/New Repair.
- Permisos directos a User, deny rules particulares, ABAC general o policy
  language.
- Reautenticación o segundo aprobador de [PBI-035](./PBI-035.md).
- Auditoría/correlation y actor persistido de [PBI-028](./PBI-028.md).
- Administración HTTP/UI de Users, roles, assignments o capabilities.
- Secret manager, enrollment productivo, release, deploy o infraestructura.

## Criterios de aceptación

1. Todos los endpoints de Repairs están registrados en una matriz cerrada y no
   existe ruta protegida sin política explícita.
2. Lecturas requieren `repairs.read`; Operational Note requiere
   `repairs.add_note`, CSRF/origen/JSON válidos y recurso scoped.
3. Cada predicado de Station, Session, User, assignment, role, capability,
   Tenant, Branch y recurso falla cerrado de forma independiente.
4. Revocaciones se observan en la siguiente decisión; no existe cache de
   grants ni autoridad en la proyección cliente.
5. D5/D6 y New Repair no son alcanzables desde HTTP/UI sin capability aprobada
   y generan cero efectos ante acceso directo.
6. Foreign/missing resources no se distinguen y client spoofing no cambia la
   autoridad.
7. Login/reload/logout/switch limpian y recomponen affordances sin filtrar el
   actor anterior.
8. PostgreSQL 18.4 material, arquitectura, contratos, UI, typecheck, build,
   dos runs y comparison quedan GREEN.
