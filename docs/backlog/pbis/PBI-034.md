# PBI-034 — Operational Session

## Estado

- **Estado:** In review — candidato de integración; no integrado ni `Done`.
- **Tipo:** Identity / Security Foundation.
- **Owner:** Producto + Seguridad + Operaciones + Ingeniería.
- **Riesgo:** Critical — clasificación preservada; es el riesgo de
  Session/identity ya previsto por el `Identity Master Goal`, no un Critical
  nuevo inesperado.
- **Estimación:** Large.
- **Sprint:** SPRINT-02 — PBI actual; WIP `1/1`.

## Objetivo

Mantener una identidad operacional atribuible dentro del contexto confiable de
una Station después de autenticar el PIN, con login, logout y cambio de User
visibles en localhost.

## Contrato aprobado

- La Station se resuelve server-side; el cliente no elige Tenant, Branch ni
  Station.
- Una sesión activa por Station.
- Un User puede operar en varias Stations cuando sus assignments lo permiten.
- Idle timeout de 60 minutos renovado sólo por actividad autenticada válida.
- Lifetime absoluto de 12 horas.
- Logout termina Session, no Station binding.
- Cambiar User exige PIN nuevo y reemplaza atómicamente la Session sólo si la
  autenticación nueva termina correctamente; un intento fallido conserva la
  Session vigente.
- Login y switch usan compare-and-set explícito contra la Session activa bajo
  el guard de Station. El switch prueba primero que el bearer/CSRF presentado
  pertenece a la Session esperada; un tab o response obsoleto no puede
  reemplazar silenciosamente a un actor más nuevo.
- User, PIN credential, assignment, Station o binding inválidos/revocados hacen
  fallar cerrada la resolución.
- El bearer de Session es aleatorio, opaco, sólo vive en cookie `HttpOnly` y la
  base conserva únicamente su digest. Replay de tokens cerrados, reemplazados,
  expirados o invalidados se rechaza.
- Las mutaciones de Session exigen origen same-origin, JSON y prueba CSRF; las
  respuestas de identidad son `no-store` y los errores de autenticación son
  genéricos.

## Transporte y persistencia

- Cookie host-only `sr_session`, `HttpOnly`, `SameSite=Strict`, `Path=/`,
  `Secure` cuando el transporte es HTTPS y máximo 12 horas.
- Token aleatorio de 256 bits; verifier SHA-256 stateful. No JWT, token raw en
  DB/API/logs ni storage del navegador.
- Cookie CSRF legible y header de coincidencia para `POST`/`DELETE`, con
  validación de `Origin`/Fetch Metadata y sin CORS.
- El challenge CSRF previo al login usa una cookie separada y acotada al
  endpoint. `GET` nunca crea, rota ni elimina el par autoritativo de Session;
  logout sólo lo expira después de cerrar exactamente bearer + CSRF dentro de
  la transacción protegida por Station.
- Los intercambios Session del navegador se serializan por origen con Web
  Locks. Una mutación invalida los snapshots de otros tabs antes de su request
  mediante BroadcastChannel sin identidad ni secretos y publica su término;
  un tab remoto oculta inmediatamente al actor y reconcilia detrás del lock.
- Las lecturas y la espera del lock tienen límite finito. Una mutación ya
  admitida no se abandona por timeout/cancelación cliente, para no perder un
  `Set-Cookie` después de un commit servidor.
- Persistencia Access-owned, guard transaccional por Station, versión
  optimista, timestamps UTC y estados explícitos.
- Un login sin cookies puede recuperar disponibilidad marcando expirada, bajo
  el mismo guard, sólo la Session activa cuya frontera idle/absolute ya venció.
- `SR_SESSION_SIGNING_KEY` permanece reservado y sin consumidor: una Session
  stateful con bearer aleatorio de alta entropía no requiere firma adicional.
- `SR_PIN_PEPPER` se valida al componer el runtime; material ausente o inválido
  impide que el proceso llegue a escuchar.

## Criterios de aceptación

1. El bootstrap local/test y la superficie de Session derivan contexto
   exclusivamente de una Station verificada server-side.
2. User elegible + PIN válido crean como máximo una Session activa por Station.
3. Login, reload, logout y cambio de User son persistentes y visibles; ningún
   fallo de cambio destruye la Session anterior.
4. Idle/absolute expiry y actividad se verifican con reloj controlado.
5. Revocación/inactividad o cambio de versión de cualquier predicado requerido
   invalida la Session al resolverla.
6. Replay, manipulación de contexto/cookies y carreras de start/touch/logout/
   switch fallan cerrados y determinísticamente.
7. CSRF/origin/cookie/cache/error contracts evitan exponer credenciales,
   tokens o enumeración útil.
8. Light/Dark, keyboard/focus y 390/768/1024/1280+ conservan un gate de login y
   actor activo coherentes.
9. PostgreSQL 18.4 material, arquitectura DEC-005, typecheck, build, dos runs y
   comparison quedan GREEN.

## Candidato materializado

El working tree de `feature/pbi-034-operational-session` materializa un
candidato de integración con este alcance acotado:

- modelo, casos de uso y persistencia Access-owned para crear, resolver,
  renovar, terminar y reemplazar una Session;
- migración aditiva con una Session activa por Station, verificadores de bearer
  y CSRF, versionado y cierre/invalidation fail-closed ante cambios de Station,
  binding, Branch, User, assignment, role o PIN credential;
- superficie `GET`/`POST`/`DELETE /api/access/session`, errores genéricos,
  `Cache-Control: no-store`, cookies host-only y mutaciones same-origin JSON con
  prueba CSRF;
- protocolo de concurrencia multi-tab con CAS servidor, lock exclusivo por
  origen, invalidación previa/final y respuestas obsoletas incapaces de
  sobrescribir las cookies autoritativas;
- bootstrap de Station limitado a local/test y UI de login, reload, logout y
  cambio de User integrada al Application Shell;
- Option A de DEC-005 materializada como policy v4 sólo para
  `access->stations` y `access->users`, mediante tokens y contratos públicos.

La verificación acotada de Option A está en
[PBI-034 Option A Verification](../../architecture-readiness/dec-005-materialization/PBI_034_OPTION_A_VERIFICATION.md).
`SR_SESSION_SIGNING_KEY` permanece reservado y **sin consumidor**: el bearer
opaco aleatorio es stateful y la base conserva únicamente sus verificadores.
Esto no materializa autorización contextual ni concede autoridad de negocio.
