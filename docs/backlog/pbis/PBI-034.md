# PBI-034 — Operational Session

## Estado

- **Estado:** In progress.
- **Tipo:** Identity / Security Foundation.
- **Owner:** Producto + Seguridad + Operaciones + Ingeniería.
- **Riesgo:** Critical — clasificación preservada; es el riesgo de

- **Estimación:** Large.
- **Sprint:** SPRINT-02 — PBI actual; WIP `1/1`.

## Objetivo

Mantener una identidad operacional atribuible dentro del contexto confiable de
una Station después de autenticar el PIN, con login, logout y cambio de User
visibles en localhost.

## Contrato aprobado

- La Station se resuelve server-side; el cliente no elige Tenant, Branch ni
  Station.
- Una sesión activa por Station.
- Un User puede operar en varias Stations cuando sus assignments lo permiten.
- Idle timeout de 60 minutos renovado sólo por actividad autenticada válida.
- Lifetime absoluto de 12 horas.
- Logout termina Session, no Station binding.
- Cambiar User exige PIN nuevo y reemplaza atómicamente la Session sólo si la
  autenticación nueva termina correctamente; un intento fallido conserva la
  Session vigente.
- User, PIN credential, assignment, Station o binding inválidos/revocados hacen
  fallar cerrada la resolución.
- El bearer de Session es aleatorio, opaco, sólo vive en cookie `HttpOnly` y la
  base conserva únicamente su digest. Replay de tokens cerrados, reemplazados,
  expirados o invalidados se rechaza.
- Las mutaciones de Session exigen origen same-origin, JSON y prueba CSRF; las
  respuestas de identidad son `no-store` y los errores de autenticación son
  genéricos.

## Transporte y persistencia

- Cookie host-only `sr_session`, `HttpOnly`, `SameSite=Strict`, `Path=/`,
  `Secure` cuando el transporte es HTTPS y máximo 12 horas.
- Token aleatorio de 256 bits; verifier SHA-256 stateful. No JWT, token raw en
  DB/API/logs ni storage del navegador.
- Cookie CSRF legible y header de coincidencia para `POST`/`DELETE`, con
  validación de `Origin`/Fetch Metadata y sin CORS.
- Persistencia Access-owned, guard transaccional por Station, versión
  optimista, timestamps UTC y estados explícitos.
- `SR_SESSION_SIGNING_KEY` permanece reservado y sin consumidor: una Session
  stateful con bearer aleatorio de alta entropía no requiere firma adicional.

## Criterios de aceptación

1. El bootstrap local/test y la superficie de Session derivan contexto
   exclusivamente de una Station verificada server-side.
2. User elegible + PIN válido crean como máximo una Session activa por Station.
3. Login, reload, logout y cambio de User son persistentes y visibles; ningún
   fallo de cambio destruye la Session anterior.
4. Idle/absolute expiry y actividad se verifican con reloj controlado.
5. Revocación/inactividad o cambio de versión de cualquier predicado requerido
   invalida la Session al resolverla.
6. Replay, manipulación de contexto/cookies y carreras de start/touch/logout/
   switch fallan cerrados y determinísticamente.
7. CSRF/origin/cookie/cache/error contracts evitan exponer credenciales,
   tokens o enumeración útil.
8. Light/Dark, keyboard/focus y 390/768/1024/1280+ conservan un gate de login y
   actor activo coherentes.
9. PostgreSQL 18.4 material, arquitectura DEC-005, typecheck, build, dos runs y
   comparison quedan GREEN.
