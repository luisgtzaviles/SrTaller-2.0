## Problema

Sin ownership y dependencias permitidas, las capacidades pueden mezclarse como ocurrió en el sistema anterior.

## Valor esperado

Proponer fronteras de responsabilidad y lenguaje para razonar sobre datos, eventos y dependencias antes de diseñar tablas o endpoints.

## Alcance

- Mapear los módulos mínimos solicitados.
- Describir responsabilidad, datos conceptualmente propios, eventos posibles, dependencias permitidas y preguntas.
- Identificar capacidades transversales sin crear un módulo genérico que concentre todo.

## Fuera de alcance

- Tablas, clases, endpoints, paquetes o servicios desplegables.
- Declarar definitivos los límites o eventos.

## Criterios de aceptación

- [x] [MODULE_MAP.md](../../product/MODULE_MAP.md) cubre los 21 módulos solicitados.
- [x] Cada módulo documenta los cinco aspectos requeridos.
- [x] El mapa evita ownership compartido sin explicación.
- [x] Dependencias circulares o inciertas quedan visibles.
- [x] Arquitectura y producto revisan los límites.

## Dependencias

PBI-003, PBI-004 y PBI-006.

## Riesgos

Diseñar módulos según pantallas o tablas; crear fronteras demasiado finas; asumir eventos inexistentes.

## Preguntas abiertas

- ¿Qué datos maestros pertenecen a Configuration, Platform o cada módulo?
- ¿Qué flujos necesitan consistencia entre módulos?

## Evidencia esperada

Mapa revisado y registro de límites/disputas pendientes.
