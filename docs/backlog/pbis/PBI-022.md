## Objetivo

Materializar la organización técnica mínima seleccionada por DEC-005 y producir
evidencia suficiente para que Arquitectura e Ingeniería puedan determinar, en
una revisión posterior y separada, si DEC-005 puede avanzar desde
`Accepted — Selection Approved / Materialization Pending` a un estado
equivalente a `Implemented / Materialized — Verification Pending`.

La materialización comprende exclusivamente:

- estructura física mínima;
- límites de los módulos iniciales;
- superficies públicas;
- reglas de imports y grafo;
- ownership;
- política de shared kernel;
- separación de infraestructura transversal;
- enforcement local determinista;
- fixtures positivos y negativos;
- mutaciones controladas;
- evidencia verificable.

Este PBI no desarrolla funcionalidad de negocio. Su ejecución por sí sola no
cerró DEC-005; la promoción se sustenta en la sexta reverificación formal
independiente posterior. Su cierre no autoriza el inicio general de R0.

## Estructura objetivo

La forma mínima permitida es equivalente a:

```text
src/
  app.module.ts
  main.ts
  startup-config.ts
  modules/
    tenancy/
      index.ts
      tenancy.module.ts
    stations/
      index.ts
      stations.module.ts
    access/
      index.ts
      access.module.ts
  infrastructure/
  shared/
```

El diagrama expresa roots, módulos y superficies permitidos; no obliga a
materializar todos los paths. Dentro de cada módulo sólo pueden aparecer, si
un artefacto técnico real lo exige, las capas aprobadas por DEC-005:

```text
domain/
application/
  contracts/
  ports/
  use-cases/
infrastructure/
presentation/
  http/
```

Reglas para materializar el árbol:

1. Los tres módulos iniciales tienen una función técnica verificable dentro del shell o checker; no son placeholders para negocio futuro.
2. Un directorio vacío, `.gitkeep`, README de relleno o archivo sin función verificable no satisface DEC005-C02.
3. Las capas internas permanecen ausentes mientras no exista un artefacto técnico permitido que deba ubicarse allí.
4. `shared/` permanece conceptualmente vacío. Como Git no conserva directorios vacíos, la ausencia física es preferible a introducir contenido ficticio.
5. `infrastructure/` raíz sólo contiene facilities técnicas de proceso; no adapters funcionales de los módulos.
6. No se crea ningún otro módulo ni raíz global.

## Grafo permitido

```text
access ─────> stations ─────> tenancy
   └────────────────────────> tenancy
```

| Productor | Consumidor permitido | Import permitido |
| --- | --- | --- |
| `tenancy` | `stations` | Sólo superficie pública `tenancy/index.ts` |
| `tenancy` | `access` | Sólo superficie pública `tenancy/index.ts` |
| `stations` | `access` | Sólo superficie pública `stations/index.ts` |

Quedan prohibidos:

- `tenancy -> stations`;
- `tenancy -> access`;
- `stations -> access`;
- cualquier ciclo directo o transitivo;
- dependencias implícitas o no registradas;
- imports profundos;
- acceso directo a internals, adapters o persistencia de otro módulo.

El checker debe comparar el grafo documentado con los imports reales. Un nuevo
edge exige actualizar y aprobar el grafo antes de introducir el import; este
PBI no autoriza ampliar el grafo.

## Superficie pública

Cada módulo expone contratos funcionales únicamente mediante su `index.ts`.

### Exports permitidos

- contratos framework-free requeridos por un consumidor real;
- identificadores o snapshots inmutables aprobados;
- resultados explícitos;
- hechos públicos estables definidos por el owner.

### Exports prohibidos

- entidades o agregados mutables;
- repositories o modelos de persistencia;
- controllers, DTOs HTTP, adapters o providers Nest;
- utilidades internas;
- reexports indiscriminados de una capa o del módulo completo;
- `<module>.module.ts` como API funcional.

### Reglas de consumo

- Un consumidor externo al módulo usa únicamente `index.ts`.
- Los imports internos pueden usar internals del mismo módulo sin convertirlos en API.
- Sólo `AppModule` puede importar `<module>.module.ts` para composición.
- Un barrel interno no puede ocultar un deep import, un ciclo o una dependencia no autorizada.
- Todo export público debe tener consumidor, propósito y estabilidad registrados.

## Capas internas y NestJS

| Capa | Puede depender de | Prohibiciones |
| --- | --- | --- |
| Dominio | Su propio dominio y shared admitido | NestJS, aplicación, presentación, infraestructura, transporte y otro módulo |
| Aplicación | Su dominio/aplicación, puertos propios y APIs públicas permitidas | NestJS, presentación, adapters, SQL, ORM y framework HTTP |
| Contrato público | TypeScript/framework-free aprobado | NestJS, transporte, persistencia y entidad mutable |
| Presentación | Aplicación propia y contratos de transporte | SQL, repositories, adapters concretos e internals de otro módulo |
| Adapter exterior | Puertos y dominio del módulo owner | Internals o persistencia de otro módulo |
| Composición Nest | Módulos y wiring técnicos autorizados | Reglas, queries, autorización o acceso a datos |

Los puertos pertenecen hacia adentro, en la aplicación que expresa la
necesidad. Los adapters pertenecen al módulo propietario. No se exige ni se
autoriza crear una arquitectura hexagonal completa o archivos sin consumidor.

## Checker local requerido

El PBI define capacidades, no selecciona arbitrariamente una herramienta.
La implementación debe demostrar que el checker:

- es determinista, rápido, no interactivo y ejecutable localmente;
- no depende de CI ni de servicios externos;
- procesa los archivos TypeScript y JavaScript relevantes;
- devuelve exit code cero sólo cuando las reglas cubiertas se cumplen;
- devuelve exit code distinto de cero ante cada incumplimiento comprobado;
- identifica regla, path, import o ciclo y ofrece diagnóstico accionable;
- detecta imports profundos y consumo de internals;
- detecta dependencias fuera del grafo y ciclos directos/transitivos;
- detecta NestJS en dominio, aplicación y contratos públicos;
- detecta presentación o infraestructura importadas desde capas internas;
- detecta `forwardRef` y `ModuleRef` usado como service locator funcional;
- detecta módulos Nest funcionales globales;
- detecta roots globales `common`, `utils`, `helpers`, `base` y `core`;
- detecta módulos y rutas vacías o anticipatorias cuando sea técnicamente posible;
- verifica que la API intermodular salga sólo por `index.ts`;
- verifica que sólo `AppModule` importe `<module>.module.ts`;
- controla contenido y admisiones de `shared`;
- documenta parser, resolución NodeNext, imports dinámicos, reexports, paths ignorados, falsos positivos y falsos negativos;
- puede repetirse dos veces sobre el mismo árbol con salida y exit code equivalentes.

Si un checker textual se usa como transición, sus límites y criterio de
sustitución deben quedar explícitos. No puede declararse suficiente si un
fixture obligatorio evade la detección.

## Fixtures y mutaciones

Los fixtures deben estar aislados del código de producto y no convertirse en
módulos o contratos reales. Cada caso registra regla, estado inicial,
mutación, resultado esperado, exit code y fragmento diagnóstico esperado.

| Caso mínimo | Tipo | Resultado esperado |
| --- | --- | --- |
| Import permitido según grafo y `index.ts` | Positivo | Exit `0` |
| Import profundo a otro módulo | Negativo | Exit distinto de `0`; identifica deep import |
| Dependencia inversa | Negativo | Exit distinto de `0`; identifica edge prohibido |
| Ciclo directo o transitivo | Negativo | Exit distinto de `0`; muestra ciclo |
| NestJS en dominio | Negativo | Exit distinto de `0`; identifica capa y package |
| NestJS en aplicación | Negativo | Exit distinto de `0`; identifica capa y package |
| `forwardRef` | Negativo | Exit distinto de `0`; identifica regla |
| Módulo funcional global | Negativo | Exit distinto de `0`; identifica `@Global` o equivalente |
| Root global `utils` | Negativo | Exit distinto de `0`; identifica carpeta prohibida |
| Root global `common` | Negativo | Exit distinto de `0`; identifica carpeta prohibida |
| Módulo anticipatorio vacío | Negativo | Exit distinto de `0`; identifica ruta |
| Export público válido | Positivo | Exit `0`; contrato framework-free aceptado |
| Acceso a internal de otro módulo | Negativo | Exit distinto de `0`; identifica productor y consumidor |

Las pruebas negativas deben demostrar primero que la mutación es rechazada y
después que el árbol vuelve a pasar al retirarla. Una prueba que sólo busca un
texto estático sin activar el rechazo no satisface el PBI.

## Política de fallo

El resultado de la ejecución es `FAIL` y no puede recomendar materialización si:

- aparece lógica funcional;
- se crea un módulo distinto de `tenancy`, `stations` o `access`;
- se crean carpetas vacías, anticipatorias o genéricas prohibidas;
- `shared` contiene un elemento no admitido;
- existe un deep import, ciclo o edge fuera del grafo;
- NestJS aparece en dominio, aplicación o contrato público;
- se usa `forwardRef`, `ModuleRef` funcional o módulo funcional global;
- el checker depende de CI, red, IDE o estado interactivo;
- una prueba negativa no activa realmente el rechazo esperado;
- ownership, superficies o grafo no coinciden con el código;
- se introduce persistencia, endpoint, autenticación u otro gate diferido;
- se modifica o resuelve DEC-049/044/050/051/063 por implementación;
- se marca DEC-005 cerrada o verificada sin revisión posterior;
- se copia SPIKE-009 como scaffold.

Todo fallo debe conservar comando, exit code y diagnóstico sanitizado. No se
relajan reglas para poner verde el gate sin autorización de Arquitectura.
