## Problema

Ambientes ambiguos y despliegues manuales impiden saber qué se probó, promueve deriva y vuelven riesgoso rollback.

## Valor esperado

Definir separación, promoción inmutable y responsabilidades operativas antes de crear infraestructura.

## Alcance

- Definir local development, staging y production con datos/credenciales separados.
- Promover el mismo artefacto versionado sin rebuild.
- Describir despliegue independiente, migración forward-compatible, rollback y feature flags futuras.
- Prohibir FTP/manual como proceso normal.

## Fuera de alcance

- Dockerfiles, Compose, workflows de GitHub Actions, cuentas cloud o secretos.
- Seleccionar hosting, registry o estrategia final de flags.

## Criterios de aceptación

- [x] [ENVIRONMENTS.md](../../delivery/ENVIRONMENTS.md) diferencia claramente los tres ambientes.
- [x] [DEPLOYMENT_STRATEGY.md](../../architecture/DEPLOYMENT_STRATEGY.md) define build/promote/deploy/verify/rollback.
- [x] Staging no usa datos reales salvo proceso controlado.
- [x] Se exige el mismo digest desde staging a producción.
- [x] ADR-007 conserva alternativas y estado Proposed.

## Dependencias

PBI-010, política de seguridad y necesidades operativas aún TBD.

## Riesgos

Secretos compartidos, artefactos mutables, migración incompatible o rollback que ignore datos.

## Preguntas abiertas

- ¿Qué plataforma, regiones, RTO/RPO y responsables operativos se aprobarán?
- ¿Qué gates de producción serán obligatorios?
