## Problema

Identidad global, membresía, rol, sucursal, dispositivo y sesión operativa son dimensiones distintas; fusionarlas permitiría acceso incorrecto o impediría operación legítima.

## Valor esperado

Establecer un modelo autorizable, revocable y auditable que soporte roles comunes y permisos personalizados.

## Alcance

- Diferenciar identidad, membresía, asignación, rol, permiso y sesiones.
- Describir PIN en dispositivo autorizado, step-up para acciones sensibles, bloqueo y revocación.
- Identificar decisiones de producto necesarias para una matriz futura de permisos.

## Fuera de alcance

- Algoritmos criptográficos, proveedores de identidad, tokens o matriz final.
- Implementar autenticación o recuperación de cuenta.

## Criterios de aceptación

- [x] [IDENTITY_ACCESS_AND_PERMISSIONS.md](../../architecture/IDENTITY_ACCESS_AND_PERMISSIONS.md) separa todos los conceptos requeridos.
- [x] La autorización siempre incluye tenant y, cuando aplique, sucursal/dispositivo.
- [x] Acciones sensibles y eventos auditables preliminares están visibles.
- [x] Revocación y bloqueo se describen conceptualmente.
- [x] Product Owner y seguridad validan el contrato conceptual mediante ADR-011/012/013.

## Dependencias

PBI-002, PBI-007 y validación de operación del taller.

## Riesgos

Roles demasiado rígidos; PIN tratado como identidad completa; permisos heredados ambiguos; recuperación insegura.

## Preguntas abiertas

- ¿Qué acciones requieren autenticación reforzada o supervisor?
- ¿Puede una identidad pertenecer a varios tenants?
- ¿Quién administra roles personalizados?

## Evidencia esperada

Modelo, escenarios allow/deny/revoke y registro de decisiones pendientes.
