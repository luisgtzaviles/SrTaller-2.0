# PBI-025 — PIN Credential Authentication

## Estado

- **Estado:** Done; Released: NO.
- **Tipo:** Identity / Security Foundation.
- **Owner:** Producto + Seguridad + Operaciones + Ingeniería.
- **Riesgo:** Critical — clasificación preservada; riesgo conocido y previsto
  por el `Identity Master Goal — Part D`, no un nuevo Critical inesperado.
- **Estimación:** Large.
- **Sprint:** SPRINT-02 — completado.

## Objetivo

Verificar que la identidad seleccionada en una Station confiable conoce su PIN
tenant-scoped, sin convertir el PIN en identidad, capability o sesión.

## Contrato aprobado

- UX `seleccionar User → ingresar PIN`.
- PIN numérico de seis dígitos.
- Credencial separada de User, nunca plaintext ni reversible.
- Salt individual, versión y parámetros gobernados.
- Cinco intentos fallidos consecutivos y lock inicial de cinco minutos.
- Rate limiting adicional por Station/User.
- Conforme al `Identity Master Goal — Part D`, este slice materializa estado,
  versión y fallo cerrado para una credencial ya revocada, pero no implementa
  un comando o superficie operacional de reset/revocación.
- Si ese lifecycle operacional se aprueba en un slice posterior, PBI-034 debe
  invalidar las Sessions activas; PBI-026 aporta la autorización por capability
  y PBI-028 la auditoría. Preparar esos consumidores no afirma que el reset ya
  exista.

El algoritmo y parámetros concretos quedan fijados por el
[threat model](../../quality/evidence/pbi-025/THREAT_MODEL.md): Argon2id nativo
de Node 24.18.0, perfil versionado de 64 MiB, tres pasadas, paralelismo cuatro,
salt aleatorio de 16 bytes, tag de 32 bytes y pepper externo de 32 bytes.

## Fuera de alcance

- Operational Session, que pertenece a [PBI-034](./PBI-034.md).
- Roles/capabilities y autorización.
- Email/password, recuperación externa, biometría o identidad global.
- UI administrativa completa, deploy o credenciales productivas.

## Criterios de aceptación

- PIN protegido, limitado al Tenant y nunca registrado.
- Respuestas y logs no permiten enumeración útil.
- Provisioning idempotente, intentos, lock, expiración, concurrencia y limpieza
  del contador/lock tras autenticación correcta se prueban server-side.
- User inactivo/revocado y credencial ausente/revocada fallan cerrados; no se
  adelanta un comando o superficie operacional de reset/revocación de
  credencial.
- El resultado autenticado todavía no concede una acción de negocio.

## Persistencia y recuperación

- Migración aditiva Access-owned con `down` explícito para entornos locales y
  efímeros; en un ambiente compartido se prefiere roll-forward y se exige
  autoridad operacional separada.
- PostgreSQL 18.4 material debe probar fresh up, down/reapply, constraints,
  aislamiento, concurrencia e idempotencia.
- El rollback elimina únicamente tablas nuevas y perdería credenciales PIN;
  por ello no se ejecuta contra datos reales dentro de este PBI.
