# PBI-032 — User Directory and Lifecycle

## Estado

- **Estado:** Done canónico; `Released: NO`.
- **Tipo:** Identity Foundation.
- **Owner:** Producto + Seguridad + Operaciones + Ingeniería.
- **Riesgo:** alto.
- **Estimación:** Large — Owner autorizado.
- **Sprint:** Sprint 01 cerrado; `Released: NO`.

## Objetivo

Materializar la identidad estable tenant-scoped de los operadores antes de
crear credenciales, sesiones o nuevos writes de negocio.

## Modelo mínimo aprobado

- `userId`, `tenantId`, `displayName`, `operationalIdentifier` nullable.
- Estados `active`, `inactive` y `revoked`.
- `createdAt` y `updatedAt`.
- User no pertenece permanentemente a una Branch.
- PIN, roles y sesiones viven en agregados separados.

## Alcance y exclusiones

Incluye provisioning server-only de un primer User por tenant, lectura
tenant-scoped y transición de estado con aislamiento tenant y `expectedVersion`.
El bootstrap es único, durable, idempotente por `clientRequestId` y no es un
endpoint HTTP. Las transiciones conservan un journal durable de respuesta para
replay idempotente y `revoked` es terminal. La interfaz de Users permanece
diferida: aunque PBI-033 aporta roles/grants persistentes, PBI-026 todavía debe
intersectarlos con identidad y contexto confiable antes de publicar
administración o lectura productiva. Excluye HR, nómina, horarios,
salario, documentos, recuperación externa, PIN, roles y autorización.

## Dependencias y criterios

Depende de PBI-024 para contexto administrativo confiable y PBI-029 para
configuración. Revoked no se reutiliza silenciosamente; desactivar o revocar no
borra historia. Deben pasar casos cross-tenant y auditoría aplicable.
