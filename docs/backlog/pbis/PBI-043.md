## Problema

La política integrada de una Session activa por Station rechaza un PIN válido
cuando otro navegador/perfil ya opera en esa Station. Esto interfiere con el
Owner, empleados y QA aunque cada perfil posea cookies independientes y el
backend pueda atribuir cada request mediante su SessionId.

## Valor esperado

Users iguales o distintos operan simultáneamente desde perfiles o Stations
confiables sin expulsarse entre sí. Cada acción conserva actor, Tenant, Branch,
Station y SessionId exactos; revocación y autorización permanecen fail-closed.

## Alcance

- Materializar [ADR-014](../../decisions/proposed/ADR-014-concurrent-operational-sessions.md).
- Admission de múltiples Sessions independientes por Station.
- `expectedSessionId=null` crea Session independiente.
- `expectedSessionId=X` reemplaza únicamente X después de autenticar bearer,
  CSRF y PIN nuevo.
- Remover el unique parcial active por Station y agregar índices de consulta/
  revocación definidos por evidencia.
- Preservar PK, verifier unique, contexto, revisions, lifecycle, timestamps y
  versionado.
- Eliminar locks station-wide de logins independientes; conservar CAS/lock
  exacto para switch y logout.
- Revocación efectiva para Session, User, Station y PIN credential/version,
  con puertos internos mínimos cuando se requieran.
- Preservar cookies, CSRF, Origin, Fetch Metadata, JSON-only, no-store,
  autorización, PIN rate limit y expiración 60m/12h.
- Cobertura Critical material y prueba Owner/QA con dos perfiles reales.
- Documentación, migration/rollback evidence y runtime provenance.

## Actores y escenarios

- **Owner/empleado:** mantiene Sessions en Mac, móvil u otra Station confiable.
- **Users distintos:** usan perfiles independientes de una misma Station.
- **QA/Codex:** inicia y termina su Session sin tocar la Session Owner.
- **Administrador futuro:** necesita revocar Session(s), pero su UI/endpoints
  quedan fuera.

## Criterios de aceptación

### Admission y browser

- [x] Dos logins independientes en la misma Station crean Sessions distintas y
  ambas aceptan operaciones autorizadas.
- [x] Un mismo User puede operar en dos perfiles de la misma Station y en dos
  Stations.
- [x] Users distintos pueden operar en perfiles distintos de la misma Station.
- [x] Switch reemplaza sólo la Session solicitante; un fallo conserva esa
  Session y todas las demás.
- [x] Logout termina sólo la Session solicitante.
- [x] Varias pestañas del mismo perfil siguen compartiendo una Session.

### Seguridad y lifecycle

- [x] Cada request deriva Tenant/Branch/Station/StationCredential y resuelve
  User/SessionId server-side.
- [x] User/Station/credential revoke invalida efectivamente todos los bearers
  afectados antes de otra operación; restore no revive Sessions.
- [x] PIN lockout impide login nuevo y no termina Sessions existentes.
- [x] Idle 60 minutos y absolute 12 horas permanecen exactos por Session.
- [x] CSRF A no autoriza bearer B; cookies y same-origin contracts no cambian.
- [x] Business audit cubierto preserva el SessionId solicitante correcto.
- [x] Errores permanecen genéricos y no filtran existencia, scope o secretos.

### Persistencia y delivery

- [x] PostgreSQL permite N activas por Station sin debilitar PK/verifier/scope.
- [x] Índices soportan resolución y revocación por Station/User/PIN credential;
  StationCredential queda sin índice adicional porque no existe una operación
  productiva ni plan material que lo justifique.
- [x] Migración fresh/existing preserva Sessions activas y no rota cookies.
- [x] Rollback con N>1 aborta; nunca elige o cierra una ganadora silenciosa.
- [x] Races de login, switch/logout y revoke/login tienen outcomes exactos y
  fail-closed.
- [x] Owner profile permanece autenticado durante login/reload/switch/logout de
  QA en otro perfil.
- [ ] Gates Critical finales, ancestry y runtime provenance quedan en evidencia sobre
  el mismo SHA.
