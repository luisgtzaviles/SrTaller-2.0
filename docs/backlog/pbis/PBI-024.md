## Problema y objetivo

Las escrituras de negocio no pueden confiar en `tenantId` o `branchId`
proporcionados libremente por el frontend. Este PBI materializa una Station
persistida y válida que permite resolver server-side un
`TrustedStationContext` inmutable con Tenant, Branch y Station.

No representa todavía el contexto operativo completo: User y Operational
Session pertenecen a PBIs posteriores.

## Alcance

- Station ID estable, tenant owner, branch binding y estados active/revoked.
- Resolución server-side y fail-closed ante Station desconocida, revocada,
  Branch inactiva o mismatch.
- Invalidación y concurrencia compatibles con PostgreSQL.
- Bootstrap técnico mínimo, gobernado y no público para disponer de la primera
  Station/binding antes de la administración completa.
- Reutilización selectiva de diseño, invariantes y tests útiles de la rama
  histórica `r0/pbi-024-trusted-station-context`.

## Fuera de alcance

- UI o API administrativa de create/link/relink/unlink/revoke.
- User, PIN, sesión, roles, capabilities o autorización de negocio.
- Integrar o cherry-pickear completa la PR draft #3.
- Deploy, Production o hardware fingerprint como autoridad.

## Criterios de aceptación

1. El servidor resuelve Tenant/Branch/Station sin aceptar esos IDs como
   autoridad del cliente.
2. Contexto ausente, inválido, inactivo o revocado falla cerrado.
3. No existe lectura o mutación cross-tenant.
4. La revocación invalida resoluciones posteriores y los casos concurrentes
   se prueban sobre PostgreSQL real.
5. El bootstrap mínimo no expone una ruta administrativa anónima.
6. La evidencia histórica se trata como insumo, no como PASS heredado.
