# PBI-024 — Apply trusted tenant, branch and station context

## Estado

- **Estado:** Ready for formal review — implementation not authorized.
- **Tipo:** R0 technical foundation / Security.
- **Owner:** Arquitectura + Ingeniería; revisión Producto + Seguridad.
- **Riesgo:** alto, fail-closed.
- **Estimación:** `L`; el camino crítico es persistencia/lifecycle →
  resolución y vigencia → PostgreSQL/aislamiento → mutaciones/evidencia →
  revisión independiente.

El
[tratamiento temporal de DEC051-C02](../../architecture-readiness/pbi-024/DEC_051_C02_TEMPORARY_TREATMENT.md)
permite este refinamiento y su revisión formal. El estado de este PBI significa
exclusivamente que el expediente está completo para dictamen. No equivale a
`Ready` de implementación, `In progress`, autorización, rama o PR funcional.
El primer merge funcional posterior a PBI-023 continúa bloqueado.

## Objetivo

Materializar, cuando exista autorización separada, un contexto inmutable de
tenant, sucursal y estación reconocido exclusivamente por el servidor. Debe
fallar cerrado ante ausencia, conflicto, manipulación, revocación, estado no
operativo o revisión obsoleta.

El resultado de PBI-024 será `TrustedStationContext`. No se denomina contexto
operativo completo porque ADR-010 exige también usuario y ADR-011 asigna esa
responsabilidad a PBI-025.

## Alcance y exclusiones

Incluye:

- DEC-009–012 en su fundación tenant/sucursal/estación;
- entidad y persistencia mínima de estación y su historial de vinculaciones;
- estados `Unlinked`, `Active` y `Revoked`;
- link, unlink/relink explícito y revocación como transiciones de dominio;
- resolución server-side, contexto inmutable y validación de revisión vigente;
- contrato público mínimo `tenancy → stations` para elegibilidad tenant-scoped
  de branch y contratos públicos mínimos del módulo `stations`;
- traducción de errores DEC-044, aislamiento, concurrencia y evidencia.

Excluye usuarios, PIN, sesiones, roles, capacidades, segundo aprobador,
frontend, endpoints, negocio, Reparaciones, clientes, equipos recibidos,
folios, pagos, observabilidad completa, secretos productivos, cache
distribuido, offline, RLS, deploy y producción.

## Dependencias

- **Satisfechas para refinamiento:** PBI-023 cerrado; ADR-004/010; DEC-004,
  DEC-005, DEC-044, DEC-049, DEC-051 y DEC-063 aceptadas.
- **Gates de una implementación futura:** DEC051-C04 y DEC063-C02/C06, revisión
  Producto, Seguridad y Arquitectura/Ingeniería.
- **Integración posterior:** PBI-025 completa usuario/sesión; PBI-026 compone
  autorización administrativa; PBI-027 aporta política temporal; PBI-028
  correlación/auditoría; PBI-029 gobierna credenciales y secretos.
- **Gate de merge:** DEC051-C02 sigue `Pending`; ningún primer merge funcional
  está permitido mientras no quede `Satisfied` o DEC-051 sea modificada por
  decisión formal separada.

## Criterios de aceptación

1. Station context sólo se resuelve server-side.
2. El cliente no puede seleccionar tenant o branch efectivos.
3. Una station válida produce un `TrustedStationContext` inmutable.
4. Una station desconocida falla cerrada.
5. Una station revocada falla cerrada.
6. Un mismatch tenant/branch falla cerrado.
7. No existe lectura cross-tenant.
8. Una revocación invalida resoluciones posteriores.
9. Toda operación protegida bloquea la station con `SELECT ... FOR UPDATE`,
   revalida contexto y ejecuta el efecto en la misma transacción; efecto y
   revoke quedan serializados, una revisión stale se rechaza y tests
   PostgreSQL demuestran ambos órdenes de adquisición.
10. Cada escenario tiene una única categoría interna DEC-044; AD-05, AD-07 y
    AD-11 se separan por causa, permiten colapso externo sanitizado y tienen
    pruebas binarias sin enumeración.
11. `tenancy` conserva ownership funcional de branch; `stations` consume su
    superficie pública sin duplicar invariantes, deep imports ni acceso directo
    a persistencia ajena.
12. Persistencia respeta DEC-049.
13. PostgreSQL `18.4` real pasa.
14. Mutaciones críticas pasan.
15. CI `run-1`, `run-2` y `comparison` pasa.
16. Evidencia DEC-063 aplicable queda completa y revisada.
17. No se implementa autenticación, PIN, roles o Reparaciones.
18. No ocurre merge funcional mientras DEC051-C02 siga bloqueando.

## Evidencia y gates

El
[expediente de refinamiento](../../architecture-readiness/pbi-024/README.md)
define arquitectura, modelo persistente, lifecycle, matriz allow/deny, errores,
pruebas, mutaciones, evidencia, riesgo, estimación y trazabilidad. Una futura
implementación debe producir PostgreSQL real, manifest, seguridad,
run-1/run-2/comparison, cleanup y dictamen independiente.

## Próxima revisión

Ejecutar una revisión formal independiente de PBI-024 para decidir si puede
autorizarse su implementación. Esa revisión debe evaluar por separado Producto,
Seguridad y Arquitectura/Ingeniería, volver a comprobar DEC051-C02 y no puede
autorizar merge funcional mientras dicho gate siga pendiente.
