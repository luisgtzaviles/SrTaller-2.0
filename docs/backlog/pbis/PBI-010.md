## Problema

Sin límites entre clientes, API, módulos, workers y recursos, el stack podría recrear mezcla de presentación, negocio y persistencia.

## Valor esperado

Ofrecer una vista común de componentes, responsabilidades, flujos y atributos de calidad que guíe evaluaciones técnicas.

## Alcance

- Describir el monolito modular, la única aplicación backend inicial, sus responsabilidades internas de API y procesamiento diferible, y los clientes consumidores.
- Ubicar PostgreSQL como motor aceptado y Redis, colas, realtime, storage e integraciones como candidatos conceptuales.
- Definir capas y dependencias permitidas sin crear estructura ejecutable.
- Reflejar que R0 conserva una sola aplicación y artefacto backend dentro del repositorio único, sin workspaces obligatorios.

## Fuera de alcance

- Scaffolding, módulos, endpoints, Dockerfiles, topología cloud o microservicios.
- Aceptar tecnologías por aparecer en un diagrama.

## Criterios de aceptación

- [x] [TARGET_ARCHITECTURE.md](../../architecture/TARGET_ARCHITECTURE.md) y [APPLICATION_ARCHITECTURE.md](../../architecture/APPLICATION_ARCHITECTURE.md) muestran límites y flujos.
- [x] API y procesamiento diferible aparecen como responsabilidades lógicas dentro del único artefacto/despliegue inicial; cualquier extracción futura queda condicionada por ADR-002.
- [x] Backend permanece fuente de verdad.
- [x] Arquitectura refleja mapa modular y controles multitenant.
- [x] Cada tecnología preliminar enlaza un ADR o pregunta.

## Riesgos

Diagrama aspiracional sin enforcement; confundir despliegues separados con microservicios; acoplar dominio a frameworks.
