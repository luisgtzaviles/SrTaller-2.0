## Problema

La API debe servir varios clientes y aplicar políticas transversales sin concentrar negocio, transporte y datos en endpoints difíciles de probar.

## Valor esperado

Definir criterios y una propuesta de framework/API que preserve módulos, contratos, seguridad y observabilidad.

## Alcance

- Comparar NestJS con alternativas razonables.
- Definir API central como fuente de verdad y límites con clientes/BFFs.
- Documentar versionado, errores, validación, idempotencia y políticas de tenant a nivel conceptual.

## Fuera de alcance

- Crear aplicación NestJS, endpoints, OpenAPI ejecutable o instalar dependencias.
- Elegir ORM, librerías de auth o detalles de transporte finales.

## Criterios de aceptación

- [x] ADR-005 incluye fuerzas, alternativas, trade-offs y criterios de reconsideración.
- [x] [APPLICATION_ARCHITECTURE.md](../../architecture/APPLICATION_ARCHITECTURE.md) separa transporte, aplicación, dominio y persistencia.
- [x] Se explica cómo todos los clientes consumen autoridad central.
- [x] Políticas tenant, auth, errores e idempotencia se consideran transversales.
- [x] La aceptación registra autoridad, revisiones, evidencia y condiciones normativas.

## Dependencias

ADR-001 `Accepted`, PBI-005, PBI-007, PBI-010 y requisitos de clientes.

## Riesgos

Acoplar dominio al framework; duplicar contratos; usar guards como única barrera multitenant.

## Preguntas abiertas

- La evidencia confirmó REST/HTTP JSON como interfaz mínima de R0; rutas, payloads, versionado y compatibilidad externa siguen diferidos.
- ¿Qué consumidores externos existirán después de R0?
- ¿Qué política de compatibilidad/versionado necesita la API?
