## Problema

El cliente actual contiene un Visual Slice 0 con CSS global y un shell de
Preview, pero no tiene tokens semánticos canónicos, tema dark/system,
aislamiento de estilos por componente, catálogo visual ni el comportamiento de
Application Shell aprobado. Continuar agregando páginas sobre esa base
permitiría que cada pantalla invente colores, responsive, estados y patrones,
e incrementaría el costo de corregir consistencia y accesibilidad después.

El Design System tampoco debe crecer sin consumidores reales ni mezclarse con
reglas de Reparaciones, identidad o backend.

## Valor esperado

Disponer de una foundation visual y un Application Shell V1 verificables que
sean el único punto de partida para las siguientes rebanadas de producto, con
temas, responsive, accesibilidad, tenant accent y gobierno consistentes, sin
crear arquitectura compartida prematura.

## Alcance

- Materializar dentro del cliente React/Vite actual la fuente única de tokens
  semánticos, escalas V1 y temas light/dark/system.
- Implementar persistencia de tema, prevención razonable de flash y un acento
  de tenant controlado con validación/derivación/fallback seguro usando sólo
  configuración sintética hasta existir una fuente confiable autorizada.
- Adoptar CSS Modules para ownership de los componentes que se creen o migren;
  mantener globales únicamente reset, tokens, temas y estilos base documentados.
- Materializar sólo primitives, controls y patterns requeridos por el shell y
  su catálogo; cualquier elemento adicional del inventario V1 necesita un
  consumidor real dentro de este alcance.
- Materializar `ApplicationShell`, header global, sidebar
  expanded/collapsed, rail y drawer móvil conforme a las dimensiones y reglas
  aprobadas.
- Migrar la navegación de las rutas actualmente disponibles sin habilitar
  capacidades futuras; Nueva reparación permanece como acción contextual.
- Crear un catálogo visual interno para los elementos materializados y sus
  estados relevantes, sin introducir Storybook.
- Cubrir teclado, focus-visible, contraste, reduced motion, touch targets,
  reflow y overlays conforme al objetivo WCAG 2.2 AA, sin afirmar
  certificación.
- Conservar el monograma/logo provisional sin iniciar branding final.
- Mantener las rutas y estados honestos del Preview; esta rebanada no convierte
  en funcionales las APIs de Reparaciones ausentes.

## Actores y escenarios

- **Actores:** operador de taller en mostrador; Product Owner; Diseño;
  Frontend/Ingeniería; Calidad/Accesibilidad.
- **Contexto:** cliente web React/Vite en desktop, laptop y móvil; datos de
  contexto sintéticos hasta que exista integración confiable autorizada.
- **Escenario principal:** el operador navega las superficies realmente
  disponibles desde un shell consistente, cambia tema y utiliza teclado o
  touch sin perder legibilidad ni contexto.
- **Casos límite:** viewport estrecho; preferencia `system` que cambia; acento
  inseguro; sidebar con navegación larga; reduced motion; contexto operativo
  ausente; error o loading de una superficie; preferencia corrupta o ausente.

## Criterios de aceptación

### Tokens y temas

- [x] Una sola fuente de CSS custom properties representa accent, surfaces,
  text, borders, semantic states y aliases del shell en light/dark.
- [x] Los componentes materializados no contienen colores, radios, sombras ni
  breakpoints arbitrarios y no duplican variantes equivalentes.
- [x] El acento base usa `#B45309` en light y `#F59E0B` en dark; derivados
  documentados pasan contraste y success/warning/danger/info no dependen del
  acento.
- [x] Un acento sintético inseguro produce un derivado o fallback verificable y
  no altera estados semánticos, layout, tipografía, radios o sombras.
- [x] Light, dark y system funcionan con persistencia, sin overrides por módulo
  y con prevención razonable y probada de flash.
- [x] Tipografía, pesos, numeración tabular, spacing, radios, elevación,
  movimiento, alturas y touch targets cumplen el contrato V1.

### Application Shell

- [x] En viewport amplio el sidebar mide `256px`; puede colapsarse a `72px` en
  contexto restringido y el drawer móvil no excede aproximadamente `320px` ni
  el viewport.
- [x] Sidebar y drawer tienen active, hover, focus-visible, disabled cuando
  aplique, scroll independiente y tooltip accesible en modo colapsado.
- [x] El header contiene controles del shell y contexto disponible, pero no
  título/descripcion de página, acciones de módulo, métricas ni identidad
  duplicada.
- [x] `PageHeader` demuestra título, descripción, breadcrumb opcional y una
  sola acción primaria dominante sin invadir el header global.
- [x] En móvil la navegación usa header + drawer; no conserva la barra superior
  de iconos del Preview actual.
- [x] Sólo aparecen rutas implementadas, autorizadas y disponibles; una
  capacidad futura no se representa como placeholder o “en mantenimiento”.
- [x] Un contexto realmente bloqueado se comunica una sola vez mediante un
  blocking banner accesible; no se inventa contexto confiable ni se repiten
  errores técnicos por pantalla.

### Componentes, catálogo y calidad

- [x] Sólo se materializan los componentes consumidos por ApplicationShell,
  navegación, PageHeader, temas y los estados que el catálogo necesita para
  verificarlos; el resto del inventario permanece dirección futura.
- [x] El catálogo interno permite revisar variantes aplicables, loading, error,
  disabled, focus, light, dark, acento seguro/inseguro y viewports de `390px`,
  `640px`, `768px`, `1024px` y `1280px`.
- [x] El catálogo no queda expuesto en Production y su política exacta de
  acceso en Preview queda documentada y verificada.
- [x] Navegación completa por teclado, orden de focus, focus-visible, semántica,
  nombres accesibles, escape/focus trap del drawer, reduced motion, contraste,
  reflow y touch targets tienen evidencia manual y automática proporcional en
  el entorno disponible; la matriz AT/cross-browser no ejecutable permanece
  explícita y no se presenta como PASS.
- [x] No se afirman certificación WCAG ni integración real con tenant,
  identidad, sucursal o estación.
- [x] Typecheck, pruebas frontend aplicables, build, checker
  arquitectónico y CI canónico quedan verdes para el SHA candidato; no se
  utiliza la aprobación de diseño para saltar un gate.
- [x] Existe evidencia comparativa desktop/mobile y light/dark del candidato,
  ligada al SHA y sin datos sensibles.

## Escenarios observables mínimos

```text
Dado un viewport móvil y navegación cerrada
Cuando el operador abre el menú y elige una ruta disponible
Entonces el drawer es accesible, cambia la ruta y devuelve el foco de forma predecible
```

```text
Dado un acento de tenant que no logra contraste suficiente
Cuando se resuelve el tema
Entonces se usa un derivado o fallback seguro sin cambiar estados semánticos
```

```text
Dado que una capacidad de la IA aún no existe en runtime
Cuando se construye la navegación
Entonces la capacidad no aparece ni se representa como placeholder
```
